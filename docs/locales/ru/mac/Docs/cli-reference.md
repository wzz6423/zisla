# Справочник интеграции `zislactl`

[English](../../../../../mac/Docs/cli-reference.md) | [简体中文](../../../../../mac/Docs/cli-reference.zh-CN.md) | **Русский** | [Другие языки](../../../README.md)

`zislactl` — общий локальный протокол состояния инструментов AI, скриптов и задач CI, интегрируемых с zisla. Он записывает состояние задач, использование и уведомления как структурированные данные в транзакциях SQLite, предотвращая частично записанное состояние. Документ определяет стабильные провайдеры, команды и ограничения полей.

## Принципы

- Состояние записывается локально; запросы, ответы и учётные данные не отправляются.
- Обновления одного ID задачи идемпотентны; читатели видят полностью зафиксированное состояние базы.
- Имена провайдеров принимают совместимые псевдонимы, но сохраняются в канонической форме.

## Локальное хранение и границы JSON

Задачи, использование и уведомления находятся в `~/Library/Application Support/zisla/ai-state.sqlite`. Запись использует транзакции SQLite; текущий протокол не записывает `ai-state.json`. Очистка задач сохраняет историю использования.

`zislactl` принимает описанные аргументы командной строки, а `list` печатает построчный текст. Интеграции и настройки продолжают использовать структурированный JSON: входные JSON/JSONL-сеансы внешних инструментов и кодирование/декодирование настроек по собственным правилам. Сам CLI использует аргументы, текстовый вывод и SQLite.

WorkBuddy и WorkBuddy AI — отдельные продукты для внутреннего и международного рынков, а не старая и новая версии одного клиента. Канонические провайдеры, хранилища, значки и глубокие ссылки остаются раздельными. Старые записи WorkBuddy с `harness` доступны; провайдер глобально не переименовывается и не переносится. ID уведомлений используют явную границу провайдера/задачи (`ai-active-workbuddy:<id>` или `ai-active-workbuddy-ai:<id>`), поэтому ручная задача WorkBuddy с ID, начинающимся `ai-`, не считается WorkBuddy AI.

### Автоматическое обнаружение Delta, Orca, WorkBuddy и WorkBuddy AI

- Delta: читает индексированные метаданные потоковых диалогов из `Library/Application Support/Delta/user_*/data.sqlite` и старой корневой базы. Архивные, бездействующие и устаревшие диалоги исключаются. Числовое использование берётся из `app_model_usage_daily`, включая чтение/запись кэша. Версия без этого журнала не сообщает автоматическое использование и не угадывает его по содержимому разговора.
- Orca: читает локальные снимки `agent-hooks/last-status.json` и состояние текущего структурированного хода чата из `agent-session-journal.db`, включая каталоги профилей и записи v1/v2/v3. Учитываются максимальные ревизии и исходный порядок ходов. Завершённые, истёкшие, удалённые и содержащие только идентичность сеансы исключаются. Достоверные пути транскриптов и закреплённые домашние каталоги учётных записей Claude/Codex также дают токены. Выборки сохраняют исходного провайдера CLI и идентичность события, поэтому обычный детектор CLI не учитывает их повторно. Общемашинные кэши Orca намеренно не импортируются как дополнительное использование.
- WorkBuddy: читает собственную `~/.workbuddy/workbuddy.db` с провайдером `workbuddy`, значком WorkBuddy и ссылками `workbuddy://chat/<id>`. Хранилище WorkBuddy AI не проверяется.
- WorkBuddy AI: независимо от WorkBuddy читает состояние, названия, модель и время сеансов из `~/.workbuddy-ai/workbuddy.db`. Завершённые, удалённые и устаревшие сеансы исключаются; более свежие `updated_at`/`last_activity_at` сохраняют видимость долгих сеансов. Используются провайдер `workbuddy-ai`, его значок и `workbuddy-ai://chat/<id>`. Интеграция обнаруживает только сеансы: `session_usage.used` — заполнение контекста, кредиты не являются USD/токенами, поэтому ни то ни другое не импортируется как оплаченные токены. Ручные числовые данные передаются через `zislactl usage`.
- Все интеграции работают только для чтения по возможности; отсутствующие/несовместимые хранилища возвращают пустые данные. Не читаются реплицированные тела диалогов Delta и тела сообщений журнала Orca. Для инструментов/версий без числового журнала используйте `zislactl usage`.

## Синтаксис аргументов

- Записывайте аргумент как `--key value` или `--key=value`. Он может встретиться лишь один раз за команду; повтор — ошибка использования, код 64.
- Значение может начинаться с `--`, как `--detail --verbose`. Исключение — флаг той же команды (`--failed` у `finish`, `--queued` у `update`): он не принимается за значение, поэтому пустая переменная без кавычек в `--detail $DETAIL --failed` всё равно отмечает ошибку задачи. Такое буквальное значение передаётся как `--detail=--failed`.
- `--failed` и `--queued` — флаги. Отдельно означают true; `--failed=false` или `--failed false` и аналогичные формы `--queued` отключают их. Остальные значения ошибочны.

## `update`

Создаёт или заменяет задачу с тем же `id`.

```text
zislactl update --id <id> --provider <provider> --title <title>
  [--progress <0-100>] [--detail <text>] [--pid <process PID>]
  [--status <running|queued|blocked|error>] [--queued]
```

- Без `--progress` интерфейс показывает неопределённый прогресс.
- `--pid` необязателен и передаётся лишь при известном процессе задачи.
- `--status` явно сообщает выполнение, очередь, ожидание пользователя или ошибку во время выполнения.
- `--queued` — псевдоним `--status queued`; без явного состояния задача выполняется. Явный `--status` важнее `--queued`.

## `finish`

```text
zislactl finish --id <id> [--failed] [--detail <text>]
```

Успешные задачи получают 100%; неуспешные сохраняют последний прогресс.

## `remove`

```text
zislactl remove --id <id>
```

Если задача отсутствует, завершает работу кодом 65.

## `clear`

```text
zislactl clear
```

Удаляет задачи, сохраняя историю использования и уведомления.

## `list`

```text
zislactl list
```

Построчно выводит состояние, провайдера, название и процент текущих задач.

## `usage`

```text
zislactl usage --provider <provider>
  --input-tokens <n> --output-tokens <n>
  [--cost <USD>] [--model <model>] [--timestamp <Unix seconds>]
```

Использование наполняет 12-часовой график и тепловую карту 7x24.

## `notify`

```text
zislactl notify --title <title>
  [--detail <text>]
  [--kind <info|success|warning|error>]
  [--side <left|right>]
```

Уведомление появляется с выбранной стороны; наведение приостанавливает автоматическое закрытие.

## `message`

Отправляет одно уведомление на обе стороны острова: слева — значок приложения и отправитель, справа — прокручиваемый текст.

```text
zislactl message --app <app> --sender <sender> --content <content>
  [--app-bundle-id <bundle id>]
```

Пример:

```bash
zislactl message \
  --app "Messages" \
  --sender "Alice" \
  --content "Meet in the conference room at 7 PM" \
  --app-bundle-id com.apple.MobileSMS
```

- `--app`, `--sender` и `--content` обязательны; `--app-bundle-id` необязателен и помогает найти значок установленного приложения.
- Переносы строк и лишние пробелы схлопываются; текст обрезается примерно до 48 символов с многоточием.
- Одна транзакция SQLite сохраняет обе записи `IslandNotice`, не меняя существующее поведение `notify`.

## Коды завершения

| Код | Значение |
| --- | --- |
| `0` | Успех |
| `64` | Неверный аргумент или подкоманда |
| `65` | Ошибка данных, отсутствующая задача или повреждённая база |
| `70` | Ошибка файловой системы или другая ошибка выполнения |
