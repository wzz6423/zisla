# v0.1.0 Preview 发版记录

## 已验证的发布结果

- GitHub `v0.1.0` 是 prerelease；Gitee 也有同 tag 的 Preview Release。
- 两端都包含 `appcast.xml`、universal DMG、universal ZIP 和 ZIP 的 SHA-256；Gitee 另外自动生成源码 ZIP 与 TAR，不是遗漏附件。
- 最终 GitHub ZIP 的 SHA-256 为 `fb4fcdc7cdccbbc2d2ffb93cbd710d9a2442e8c3613c994b4caefea5ba90ce61`，与最终 appcast 的 enclosure 长度和 EdDSA 签名对应。
- App 的 `CFBundleVersion` 是 `1`，使用 ad-hoc 签名；下一次无论 Preview 还是 Release，构建号必须大于 `1`。
- 最终应用主程序与 Sparkle 组件均包含 `arm64`、`x86_64`。早期临时目录中的单架构包不是发布物，不能再次上传。

## 以后必须保持的顺序

1. 先完成所有构建、签名、公证（如有）和 ZIP 生成。
2. 基于这个最终 ZIP 生成 appcast。
3. 上传 ZIP、DMG、SHA-256 和 appcast；要替换时四个文件作为同一批次更新。
4. 读取远端 appcast 和 ZIP，核对 enclosure URL、长度、SHA-256 与本地最终产物。
5. Gitee 单独创建或更新同 tag Release 并上传同一批四个文件；GitHub 镜像不会同步 Release 附件。

## v0.1.0 后的版本策略

Preview 和 Release 共用全局构建号。示例：

```text
v0.1.1-preview.1  -> 2
v0.1.1-preview.2  -> 3
v0.1.1             -> 4
```

Release 包自动跟踪 Release，Preview 包自动跟踪 Preview。用户在设置中手动选择另一通道并点击检查后，只要目标版本的构建号更高，Sparkle 会用同一套签名和安装流程完成更新；安装完成后，新包再按自身通道自动更新。若目标构建号更低，Sparkle 会拒绝安装；这种真正的回退只能手动安装 DMG。
