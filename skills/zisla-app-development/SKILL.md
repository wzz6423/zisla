# zisla 应用开发

在修改 zisla 的功能、行为、测试、构建脚本、发布流程或安全边界时执行本技能。目标是以最小变更修复明确问题，并为修改新增可执行、可重复的测试证据；不把自动化测试或代码阅读伪装成真实使用体验。

## 不可替代的职责边界

- 由 AI 阅读代码、定位影响范围、实施最小补丁、编写并运行可隔离的自动化测试，记录机器可观察的证据。
- 由开发者在目标 macOS、真实账号、外接显示器、权限弹窗、输入设备和网络条件下亲自完成真实体验验收。要求 AI 在交付中列出待体验步骤和预期现象，但不得点击、观察或声称已完成这些步骤。
- 不得把 `swift test`、构建成功、截图、模拟器、mock、代码审阅或其他代理报告写成“已人工体验”“GUI 已验证”“真机已验证”。只有开发者明确反馈的结果才能标为人工通过。
- 不得为凑测试数量引入无断言 case、仅覆盖实现细节的 case、长时间随机测试，或会操作真实用户数据、凭据、系统设置、生产服务的 case。

## 先建立改动契约

1. 先读取相关实现、调用方、现有测试、构建/CI 入口和局部 `AGENTS.md`；开始时记录 `git status --short`，保留所有无关脏改动。
2. 将需求改写成可观察的行为契约：触发条件、输入、输出/状态变化、失败方式、兼容性以及不得改变的行为。
3. 列出拟修改文件及其原因，逐一说明为什么不能复用现有类型、测试辅助工具或测试 case。发现需求不清、多个产品语义都合理，先请求开发者决策。
4. 为每条行为契约标出风险：数据丢失、隐私/权限、外部输入、并发/生命周期、系统集成、迁移/兼容、性能、UI/可访问性。依据风险选择下面的测试层；不适用的层必须说明理由。
5. 在变更前写出开发者体验清单。使用 [references/developer-experience-acceptance.md](references/developer-experience-acceptance.md) 区分“待开发者亲验”和“机器已验证”。

## 最小修改机制

- 只修改实现行为、测试和必要文档所需的最小文件与最小代码路径；不顺手重命名、格式化、升级依赖、重排无关代码或修复不相关问题。
- 优先在现有模块、抽象、依赖注入点、fixture 和断言辅助工具内扩展；新增抽象前先证明现有路径不能表达该测试或行为。
- 保持公开 API、持久化格式、设置默认值、权限模型和可见 UI 不变，除非需求明确要求改变；改变时写出迁移、回滚和兼容测试。
- 所有源码、测试、脚本和配置中的注释必须使用英文，包括行注释、块注释、文档注释以及 `TODO`、`FIXME`。只在逻辑不自明时添加注释，并解释原因或约束，不复述代码行为。
- 修改已有代码时，将本次编辑范围内遇到的非英文代码注释一并翻译为英文；不为此扩大到无关文件或未触及代码。不得把用户可见文案、本地化字符串、测试夹具、正则内容、Markdown 数据或命令输出当作代码注释翻译。
- 每次补丁后检查 `git diff --check` 与限定路径的 diff。若发现非本任务修改、并发写入或测试产物，停止扩大改动，保留并报告它们。
- 不用“重写”“全量替换”“清理代码”掩盖需求不明。先写能复现旧问题的失败 case，再作最小修复；确实无法先写时，记录阻碍和替代证据。
- 不得在工作区生成过程性文档文件：分析报告、排查记录、方案说明、进度总结、验证报告、交接说明等，包括 `report`、`reports`、`docs` 目录下的新增说明和任何 `*-REPORT.md`、`*-分析.md`、`*-总结.md` 之类的文件。这些内容只写进对话交付，不落盘、不加入 git 索引、不提交、不推送。
- 只有开发者明确指定文档路径并要求写入时才新增或更新文档文件；此时只改该路径，不额外生成配套文档、索引或副本。

## 消融实验

每次开发在提交前必须对本次所写的代码做消融实验，只保留能被证伪的代码。

1. 列出本次引入的每个可独立移除的单元：分支、条件判断、参数、默认值、配置开关、`try`/`catch`、`guard`/`if let` 兜底、重试、回退实现、缓存、抽象层、包装函数和日志。
2. 逐个临时删除或禁用该单元，重跑与它对应的测试和验证命令，记录是否出现可复现失败。
3. 没有失败能证明其必要性的单元必须从补丁中删除，不得以“防御性”“更健壮”“向后兼容”“以后可能需要”为由保留。
4. 消融后仍需保留的单元只有两类：消融实验产生了可复现失败，或它覆盖外部系统的真实失败模式且已有对应故障注入 case 断言其行为。两类都要在交付记录中给出对应证据。

明确禁止保留：没有任何调用路径能触发的回退分支、吞掉错误后继续执行的 `catch`、对上游已校验或类型上不可能为空的值再判空、与既有校验重复的参数检查、没有测试覆盖的开关和降级路径、只做一次转发的包装函数、复述代码行为的注释。

消融实验只作用于本次改动引入的代码，不借它删除既有代码路径；发现既有代码存在同类冗余时，报告位置并等待开发者决定，不在本次补丁中一并清理。

## 调试服务的单一入口

- 对需要实际启动 macOS 调试应用的排障，只使用仓库根目录的 Makefile：首次启动使用 `make run`；代码变更后重建并重启使用 `make update`；明确结束本次 AI 调试服务时使用 `make stop`。`make update` 当前与 `make run` 使用同一受控服务生命周期。
- 不得绕过 Makefile 直接执行 `mac/Scripts/dev-service.sh`、构建产物、`open`、`launchctl` 或手工启动 `zisla-debug`；不得同时启动第二个调试实例。不得用裸 `kill`、`pkill` 停止该服务。
- 发现已有用户或 AI 启动的受控调试服务时，不等待用户手动退出，也不另起进程竞争。继续进行不依赖运行实例的代码阅读、日志分析和隔离测试；需要刷新实际应用时直接执行相应的 `make update`，让同一 Makefile 先串行停止并清理已跟踪服务，再构建和启动唯一实例。
- 若 Makefile 报告无法停止、构建或启动，先保留错误输出并进行只读诊断；不得绕过其进程匹配范围强杀未知进程。只有需要停止 Makefile 未管理的实例或会影响用户进行中的操作时，向开发者说明 PID/命令证据并请求决定。
- 在交付记录实际使用的 Makefile 命令、服务重启是否发生及结果；不得将 `make -n`、日志读取或进程检查标为真实交互验收。

## 编写可执行测试 case

将 case 放入与被测模块对应的既有测试目标：Core 放入 `mac/Tests/ZislaCoreTests`，服务与系统适配逻辑放入 `mac/Tests/ZislaKitTests`，应用行为契约放入 `mac/Tests/ZislaTests`，shell 构建/打包行为放入 `mac/Tests/ScriptTests`；Web 使用已有 `Web/` 测试工具链。测试必须验证外部可观察契约，而不是私有实现调用次数。

每个新增或改动的行为至少覆盖：正常路径、空/边界输入、无效输入或依赖失败、状态不变性/资源清理，以及此前回归路径。为每个 case 写清确定的前置状态、唯一断言目标和失败信息；固定时钟、随机源、网络和文件系统边界，避免 `sleep` 竞态和真实互联网依赖。

按风险从 [references/test-matrix.md](references/test-matrix.md) 选择并实际实现下列层级：

| 风险或变更 | 必须考虑并按需写入的 case |
| --- | --- |
| 纯函数、模型、解析、配置 | 单元、属性/边界、回归 |
| 跨模块、数据库、文件、CLI、网络适配 | 集成/系统契约、失败和恢复、升级兼容 |
| 可启动性、关键路径、打包 | 快速 smoke、构建/安装包结构检查 |
| 不可信输入、权限、凭据、路径、HTML/URL/SQL、下载 | 安全负向 case、输入净化、权限和泄漏断言 |
| 解析器、序列化、命令行参数、迁移、协议输入 | 有种子且有预算的 fuzz/属性 case 和最小回归语料 |
| 取消、并发、重试、部分写入、网络/系统服务不稳定 | 隔离的 chaos/故障注入 case：超时、拒绝、损坏、资源不足、重复/乱序事件和恢复 |
| 热路径、循环任务、大文件/大量记录、生命周期 | 性能/资源上界、取消与泄漏检查；仅在稳定环境设阈值 |
| 设置、数据库或协议格式演进 | 升级、旧数据读取、失败回滚和明确的降级策略 |

将“安全、系统、smoke、chaos、fuzz”视为风险类别而非固定名额：高风险改动缺少对应 case 时不得交付；低风险改动不适用时，在验证报告写出原因。例如仅改静态文案通常不需要 fuzz；修改 JSONL 读取器不能因已有单测而省略 fuzz 和损坏文件恢复 case。

## 安全与破坏性测试约束

- 用临时目录、假密钥、loopback/mock 服务和依赖注入构造攻击与故障；绝不读取、输出或提交真实 Token、Keychain 项、用户剪贴板、浏览历史、邮件、笔记和生产数据。
- 对路径遍历、符号链接、权限、SQL/命令/HTML/URL 注入、超大/截断输入、并发读写、取消、重复事件和部分持久化，断言拒绝/安全失败和无副作用，而不只断言“不崩溃”。
- 让 fuzz case 使用固定 seed、显式时间/输入预算、可复现失败语料和最小化机制；将长时随机探索放入手动或定时任务，不作为默认 PR 门禁。
- 让 chaos case 经接口或注入 seam 模拟超时、错误、权限拒绝、磁盘满、进程退出和损坏数据；不得真的断网、终止用户进程、耗尽磁盘、改动系统设置或攻击外部服务。
- 为性能 case 记录场景、机器/SDK 条件和预算依据。环境噪声大的指标只报告趋势，不能设为偶发失败的强制门禁。

## 运行、隔离与清理

1. 先运行与改动直接对应的最快 case，再运行该模块测试、必要的集成/脚本测试，最后运行与风险相称的构建或 smoke 检查。使用仓库既有命令；运行 Swift 测试时优先将 `swift test --scratch-path` 指向本次创建的唯一临时目录，避免在脏工作区留下 `.build`。Web 常用入口为 `npm --prefix Web run typecheck`、`npm --prefix Web run test` 和 `npm --prefix Web run build`（仅在对应变更相关时执行）。
2. 为新增临时文件、数据库、模拟服务和构建缓存创建唯一的 `mktemp -d` 目录，记录精确路径；测试结束只删除本次创建且已确认的路径。不得删除预存的 `.build`、`dist`、用户数据或其他未确认目录。仓库级清理只在开发者明确要求时执行仓库根目录的 `make clean`，它会先停止调试服务再删除 `outputs`、`mac/dist`、`mac/.build`、`Web/dist` 等本地调试与发版产物；不得自行拼接 `rm -rf` 代替它。
3. 将高成本 fuzz、chaos、性能和真实系统集成测试设计为显式 opt-in；默认测试保持快速、离线、确定、可并行。若它们进入 CI，设置确定预算、超时、资源上限和失败语料归档规则。
4. 失败时保留最小可复现输入和不含敏感信息的日志，修复根因后重跑相关 case；不通过删除、放宽断言、随机重试或 `skip` 来制造绿色结果。

## 交付与人工验收交接

交付时按以下四部分报告，缺一不可：

1. **最小变更**：文件、行为契约、未修改的兼容边界，以及为何修改范围已最小。同时列出消融实验：被消融的每个单元、消融后的失败证据或删除结论。
2. **自动化证据**：新增/更新 case 按层级列出；每条命令、通过/失败/未运行状态、case 数量和真实输出。将“未运行”如实标出。
3. **开发者亲验清单**：从 [references/developer-experience-acceptance.md](references/developer-experience-acceptance.md) 选择与此次风险相关的步骤，逐项标为“待开发者亲验”；不得预填通过。
4. **残余风险**：未覆盖或环境不能自动验证的内容、fuzz/chaos 的预算边界、外部系统限制和后续建议。

只有在开发者返回具体体验结果后，才把相应项目改为“开发者已通过”或“开发者发现问题”。
